# 知流

**一句话：让用户看见自己正在接触的信息。**

## 1. 问题

推荐系统每天都在理解你。它知道你在哪一类内容上停得久、哪一类划得快，
并且会据此决定明天给你看什么。

但你自己回答不了同一个问题：

> 我最近，到底一直在看什么？

浏览是连续的，反思是缺失的。你能回忆起某一篇让你有共鸣的回答，
却说不出这一个月里自己的信息输入是什么形状。
这不是记性问题——**没有人给过你那份视图**。

知乎上这件事尤其明显：同一个问题下的回答动辄几千字，语义密度高、观点分叉多。
"我点过哪些分类"根本描述不了你实际接触了什么。

## 2. 产品

知流是一块嵌在知乎阅读场景里的轻量仪表盘。

**你照常刷知乎就够了。** 没有要维护的清单，没有要打的标签，
也没有"今天记录一下"的仪式。当你真的停下来读完一篇回答或文章时，
知流把这篇内容理解成 1–3 个核心概念，在本地累计成：

- **最近主题分布** — 最近 20 篇里各概念的占比
- **主题趋势** — 某个概念是在变多还是变少
- **信息集中度** — 最近的内容是否集中在少数几个概念上

面板停在正文左侧量出来的空白里，深色、克制、不遮挡正文，也不弹窗打断你。

**它不改变你的推荐，不主动干预你的阅读，也不评价你读的东西。**

## 3. 为什么是知乎

三条，每条都决定了产品形态：

**① 内容够长，才值得"理解"而不是"分类"。**
短内容 Feed 里，一条内容承载的语义有限，标签化就够用了。
知乎的回答是长文本——一篇三千字的回答里，作者真正在追问的东西
往往一次都没被直接说出口。这种内容必须被**理解**，不能被数词频。

**② 同一个问题下观点是分叉的。**
"要不要考编"下面既有劝进的也有劝退的。用户读了哪一边、连着读了多少篇，
是完全不同的信息暴露结构，而这件事在任何分类体系里都看不出来。

**③ 知乎官方直答理解的就是这一类中文长内容。**
它不是通用 API，是在这个语料上长出来的能力。用它来理解知乎正文，
是这个产品里 AI 最不可替代的一处。

## 4. AI 的作用

AI 在这里**不是用来生成更多内容的**。

它做的是一次压缩：

```
连续的、非结构化的阅读
        ↓
可累计、可比较的信息暴露结构
```

一篇讲"我把跳槽的念头压下去的第三年"的回答，通篇可能一次"稳定"都没出现。
按词频它会被归到别处；按它在追问什么，它就是关于**稳定**。
这一步只有语言模型做得了。

**production provider：知乎官方直答（`zhida-fast-1p5`）。**

我们不宣称它比别的模型更准确。事实上在我们自己的验收集上，
它和本地 14B 的质量差别**测不出来**（见第 8 节）。
选它的理由是延迟与资源占用更适合线上运行——这是工程判断，不是准确率判断。

## 5. 技术架构

```
Chrome Extension（MV3）
  │
  ├─ 有效阅读判断        可见停留 ≥ 8s 才算一次，划过去的不算
  ├─ 页面类型识别        只处理回答页与专栏文章，其余一律不碰
  ├─ 正文提取            按语义容器定位，不是全页抓文本
  │
  ▼  只发送：标题 + 正文 + 公开内容 ID（字段白名单强制）
公网 HTTPS 分析服务（Vercel Serverless）
  │
  ▼
知乎官方直答  →  1–3 个核心概念 + provenance
  │
  ▼  只返回概念，不返回也不存储任何用户状态
Extension 本地存储
  ├─ 同义归一（31 个 canonical 概念）
  ├─ 最近 20 篇窗口聚合
  ├─ 趋势判定 / Simpson 信息集中度
  ▼
Dashboard
```

**历史画像与跨文章聚合全部在本地完成。** 服务端是无状态的：
它每次只看到当前这一篇，不建库、不留存正文、不做跨请求画像。

## 6. 信息集中度

它只描述一件事：**最近读的内容是否集中在少数几个概念上。**

数值来自 Simpson 指数（各概念占比的平方和），固定 20 篇窗口，
不足 10 篇不出分——样本太少时给一个数比不给更误导。

面板上就写着一行字：**"不代表好坏，只描述最近读的内容是否集中在少数几个概念上。"**

它**不**诊断信息茧房，**不**判断认知偏差，**不**评估用户健康程度。
这不是谦虚，是产品边界：一个只看得到你 20 篇阅读记录的工具，
没有资格对一个人下这种判断。集中可能是你在认真研究一件事，
也可能是你被困住了——**知流不知道，也不假装知道。**

## 7. 隐私

**长期阅读画像和跨页面聚合保存在本地。**
阅读历史、主题分布、趋势、集中度都存在浏览器里，从不上传。

**服务端仅处理当前内容。** 每次请求只包含标题、正文和一个公开内容 ID
（那是**内容**的标识，不是**用户**的标识）。这是用字段白名单强制的：
出现 `userId` / `sessionId` / `history` / `previousConcepts` / `concentration` 等字段，
服务端直接 400 拒绝——客户端在物理上无法夹带用户状态。

**我们不宣称"服务器技术上绝对无法关联请求"。**
逐篇请求终究会到达服务端，同一来源的请求序列加上到达时间，
在网络层理论上仍可被重建。代码层面阻止不了这件事，所以不做那个承诺。

## 8. 当前验证

| 能力 | 状态 | 证据 |
|---|---|---|
| 知乎回答页正文识别 | ✅ 真人在真实页面验证通过 | `contentType:answer` / `strategy:semantic` / 正文 364 字 |
| 知乎专栏文章正文识别 | ✅ 真人在真实页面验证通过 | 1818 字（结构化截断真实触发） |
| 面板不遮挡正文 | ✅ 真人验证（回答页 @1450px） | `protectedContentLeft 209` / `overlaps false` |
| 知乎官方直答 | ✅ API 实测通过 | 端点 / 三个模型名 / 响应形状全部实测；29 条验收集全量跑通 |
| 知乎搜索 API | ✅ API 实测通过 | 4 次查询全 `Code:0`；**但没有放进主链路**，理由见第 9 节 |
| 公网端到端链路 | ✅ 实测通过 | 扩展 → Vercel → 直答 → 概念，总耗时 3.1s |
| 未支持页面 fail closed | 设计为 fail closed，有测试覆盖 | 修复只有合成测试，未经真人在真实列表页复验 |

**一个已知的不确定性：** 直答没有 `temperature` 控制（传了会被静默忽略），
所以同一段正文重复分析可能给出不同结果 —— 实测撞到过一次空概念、一次
`算法推荐`。产品里影响有限（同一篇内容有 30 分钟去重窗口，不会反复分析），
但如果你拿同一段文字连试两次，看到不一样是正常的。

**我们不报告"准确率"。** 概念抽取的质量用 29 条跨领域验收集 + 独立盲评衡量，
而那套语料是作者手写的合成内容，不是真实知乎正文——
所以它能说明"这个模型在这类任务上表现如何"，不能说明"知流在真实知乎上的准确率是多少"。
后者我们还没有证据，因此不说。

## 9. 为什么没有把知乎搜索放进主链路

这是一个**证据驱动的取舍**，值得单独说。

早期设计里，知乎搜索是要进主链路的：用检索到的社区语料给概念判断提供证据。
听上去很合理，也很容易讲成"我们深度整合了知乎生态"。

然后我们做了一次 100 条盲测，把四个证据层逐层加进去做 McNemar 检验。
结果：**p 值在 0.125–1.000 之间，测不出任何增益。**

今天拿到真实 API 之后又验了一次：把概念标签直接当 query 搜，5 个词里
3 个返回的讨论一看就懂，1 个重复返回同一问题，1 个**串台**——
"算法推荐"搜出来的是推荐系统的工程论文，不是"被算法喂养"的读者语境。

所以知流**没有**为了 API 调用数量堆功能。搜索保留为未来的解释/溯源能力
（用户点开某个概念时展示"知乎上大家在这个主题下讨论什么"），
但它不进分析主链路、不阻塞面板更新。

**接了几个官方 API 不是产品价值。API 的不可替代性才是。**
直答是不可替代的——它替掉了整个本地模型；搜索目前不是。

## 10. Demo

用户连续读了几篇相近主题的内容：一份不会消失的工作、在同一个岗位待满十年、
父母眼里的好工作……

面板上"稳定"的占比一路从 30% 走到 57%，信息集中度从 10 升到 36。

用户第一次意识到：

> 我最近的信息输入，原来这么集中。

不是被告知的，是**看见**的。这中间没有任何一句评价。

## 11. 未来

- 支持更多页面类型（展开折叠、万字长答、视频回答）
- 自定义观察窗口（不只是"最近 20 篇"）
- 可选的知乎语境解释：点开某个概念，看知乎上关于它的真实讨论
- 用户自主导出自己的信息暴露记录

**不做的：** 主动推荐、信息对冲、"为你平衡视野"。
那些东西又会变成一个替用户做判断的系统——而知流的全部主张就是把判断还给用户。
