### 但 5000 不等于你能连着打 5000 次 —— 这是本轮最重要的发现

第一次跑 29 条验收集（背靠背、无间隔）：

```
as-01 … as-12   HTTP 200   （12 条全成功，耗时约 40 秒）
as-13 … as-29   HTTP 429 rate_limit_exceeded   （连续 17 条全挂）
```

跑完查额度：`zhida_openai` 的 `TotalUsed` = **14**（12 条成功 + 之前 2 次 probe）。

结论有三条，每条都影响产品：

1. **429 不扣日额度。** 401 / 400 也不扣。只有真正产出的请求扣。
2. **限速和日额度是两套东西。** 日额度很宽（5000），但瞬时速率很窄。
3. **限速是概率性的，不是一个干净的阈值。** 另一次探针以约 13.5 秒间隔连打 20 次，
   仍在第 16 次撞到一次 429，之后自己恢复。所以**退避不是优化，是必需**。

加上 5 秒间隔重跑，29 条全过，全程只多用了 1 次重试。

**对产品的意义**：真实用户是一篇一篇读的，两次分析之间至少隔几十秒，正常不会撞限速。
**会撞的是批量操作** —— 跑 benchmark、给演示预热数据、一次性回填历史。这些必须限速。

4 次真实查询：`社交焦虑` / `AI 替代工作` / `大学生就业稳定` / `亲密关系压力`，各 `--count 5`。
全部 `Code: 0`，延迟 **0.67–0.97 秒**（经 `zhihu-cli` 转发，含 CLI 进程开销）。
脱敏样本存 `fixtures/live/zhihu-search-20260913.json`。

另外用 `server/api-probe.ts` 走**知流自己那条原生 HTTP 路径**又打了三次
（`社交焦虑` / `拖延` / `消费观`），报告存 `bench/api-probe-report.json`：

这份报告同时独立回答了下面那个 `AuthorAvatar` 的疑问。

   但脱敏方式仍然该改：留成 `"AuthorAvatar": "<redacted>"`，保住"字段存在"这个事实。
2. fixture 是官方 `zhihu-cli` 打出来的（见文件里的 `_source`），
   **不是** `packages/core/src/zhihu-client.ts` 那条路径。

   它对账了官方文档声明的 14 个字段：**一个都不缺**，且多返回一个
   文档未声明的 `AuthorSignature`（已补进 `types.ts`，标为 optional）。

### Search 对知流到底有没有价值

先说不成立的那条：**它不能提高主题分类准确率。** 第四轮的 grounding 实验已经否掉过，
今天的数据没有给它翻案 —— 搜索返回的是「和这个词相关的讨论」，不是「这篇文章属于哪个主题」。

成立的是这条：**它能回答「为什么归到这个主题」。** 把概念标签直接当 query 搜，实测结果：

| 概念 | 前 3 条标题 | 判断 |
|---|---|---|
| 考公考编 | 考公务员在大学应该选哪些专业 / 大量年轻人扎堆考公考编，理性还是跟风 / 中国的考公考编还能火多久 | ✅ 一看就懂 |
| 拖延 | 克服懒惰和拖延的最好方法 / 拖延症有哪些实用的克服方法 / 要怎么做才能改掉拖延的毛病 | ✅ |
| 消费观 | 月薪三千到上万的同事都在点拼好饭，消费观在变吗 / 好的消费观是怎样的 / 什么才是合理的消费观 | ✅ |
| 亲密关系 | 建立高质量亲密关系的底层逻辑 / 为什么有些人越痛苦越离不开对方 ×2 | ⚠️ **同一条重复出现** |
| 算法推荐 | 浅谈推荐算法的 Dense Scaling / 腾讯：LLM 推理引入召回 / Netflix：LLM 直接当精排 | ❌ **串台** |

最后一行是真问题：用户读的是「我被推荐算法喂了什么」，搜出来的是**推荐系统工程论文**。
同一个词在知乎有两个完全不同的语域，直接展示会让读者困惑。

**所以 Search 的现实角色是 C（related community context）+ 有条件的 B（provenance），
不是 D（semantic adjudication），更不是提高准确率。** 落地必须带两个约束：

1. 按 `Title` 去重（实测同一问题会重复返回）。
2. 对**有歧义的概念词**要么不展示，要么把原文正文一起送进 query 而不是只送标签。

并且：**Search 不进主链路、不阻塞面板更新**，只在用户点开某个概念时才去取。

## 四、知乎直答（`zhida_openai`）· 真实 schema

```
POST https://developer.zhihu.com/v1/chat/completions
Authorization: Bearer <access_secret>
X-Request-Timestamp: <unix 秒>
Body: 只有 model / messages / stream 三个字段
```

### 旧假设对了四条，错了两条

| 项 | 本轮之前的状态 | 2026-09-13 实测 |
|---|---|---|
| endpoint `/v1/chat/completions` | 未核实 | ✅ VERIFIED |
| Bearer + `X-Request-Timestamp` | 只在 search 上核实过 | ✅ 直答同样适用 |
| `zhida-fast-1p5` / `zhida-thinking-1p5` / `zhida-agent` | 未核实 | ✅ 三个都在。瞎编一个 → `400 model_not_found`，**服务端真的在校验**，说明这三个名字不是我们自己编的 |
| 响应是 OpenAI 形状 | **假设** | ✅ `choices[0].message.content`，`finish_reason: "stop"` |
| 可以用 `response_format` 逼出 JSON | 代码里已刻意不用 | ❌ **传上去 HTTP 200 静默忽略**，既不报错也不生效。`temperature` 同样。**直答没有 JSON mode** |
| `X-Request-Timestamp` 构造一次就行 | 旧实现这么写的 | ❌ **服务端校验它**。旧实现在构造函数里算一次，长跑进程会一直带着过期的戳 |

后两条都在代码里改掉了，并各配了一条回归测试。

### HTTP 200 是不是可能是假成功？

**不是。** 实测三种失败都是诚实的非 2xx：

```
无效 secret      → 401  {"error":{"code":"invalid_api_key","type":"authentication_error"}}
不存在的模型     → 400  {"error":{"code":"model_not_found"}}
超速            → 429  {"error":{"code":"rate_limit_exceeded"}}
```

所以 `resp.ok` 可以当作**传输层**成功的判据。但产品里仍然只有
schema 校验通过才返回 `status:'llm'` —— HTTP 200 从来不等于业务成功，这条没松。

## 五、直答 vs 本地 14B（同一套冻结验收集）

输入、prompt（`v3-shape`）、校验、统计口径**完全相同**，只换 provider。
判分由**独立盲评 agent** 按 R5 冻结的 `RUBRIC.md` 做，A/B 字母在每条 case 内部独立随机指派。

| | qwen2.5:14b | zhida-fast-1p5 |
|---|---|---|
| **单次** schema 成功 | **29/29** | **28/29**（`as-23` 第一次畸形输出，第二次成功） |
| 重试后 schema 成功 | 29/29（`attempts` 全为 1） | 29/29 |
| 多主题召回 | 6/6 | 6/6 |
| unknown 正确 | 2/2 | 2/2 |
| false unknown | 0 | 0 |
| 单主题凑数 | 10/21 | **6/21** |
| 不同概念数 | 24 | 23 |
| **p50 延迟** | **9354 ms** | **2218 ms** |
| p90 延迟 | 11278 ms | **2984 ms** |
| 最大延迟 | 50765 ms（冷加载） | 4824 ms |
| **本机常驻内存** | **9.5 GB** | **0** |
| 配额成本 | 0 | 29 次 / 5000 |

> **两个 29/29 不是一回事。** 直答的 29/29 是**重试后**的数字，单次是 28/29 = 96.6%，
> **没过** `RUBRIC.md` 冻结的 Gate 1「schema success ≥ 98%」。14B 的 29/29 是单次。
> 第一版这张表把两个 29/29 并列在同一格，那是把重试后的数字和单次的放在一起比。
>
> 而且那次重试**不是限速**：`run-zhida.ts` 设 `backoffBaseMs: 5000`，而 as-23 的
> `latencyMs` 是 4824 < 5000，所以第一次是内容层失败（畸形 JSON）后立刻重试成功。
> `extraAttempts: 1` 这个字段名（原叫 `rateLimitHits`）曾让人读成「只多用了 1 次限速重试」。

### 质量：这套盲评**测不出**两者的差别

原本这里写的是「分差 +0.103，按 RUBRIC 的并列裁决口径 <0.25 算打平」。
那个推理不成立，而且有一个可以直接测的反驳方式：
**让不同的判官重判同一份输出，看波动有多大。**

测了。**同一份 `qwen2.5:14b` 的输出**（`bench/model-select/runs-qwen2_5_14b.json`，
逐字节相同），三个独立判官、同一份冻结 rubric：

| 判分轮次 | 14B 的平均主分 | 0 分条数 |
|---|---|---|
| R5（三系统 packet，2026-09-07） | **1.8276** | 0 |
| R8（两系统 packet，含 confidence） | **1.6552** | 1 |
| R8b（两系统 packet，去掉 confidence） | **1.4828** | 2 |

**判官间极差 = 0.3448。** 而两个系统的差是 +0.103（R8）/ +0.172（R8b）。

也就是说：**这个仪器的噪声是它要测的效应的 2–3 倍，而且比 rubric 冻结的
0.25 并列阈值本身还大。** 拿它判定 0.1 量级的差异，测到的是判官身份，不是模型质量。

所以结论不是「两个模型打平」（那是关于模型的断言），而是：
**这套 29 条盲评 rubric 分辨不出这两个系统的质量差别。** 这是关于仪器的断言，
证据比原来那个 p 值强，而且是本轮自己测出来的。

### 两轮判分一致的地方（这些才是可用的信号）

判官换了、绝对分数漂移了 0.34，但**符号是稳定的**：

| | R8（含 confidence） | R8b（去掉 confidence） |
|---|---|---|
| 直答赢 / 14B 赢 | 5 / 2 | 6 / 2 |
| 双侧符号检验 p | 0.453 | 0.289 |

两轮都**不显著**。（第一版这里写的 `p ≈ 0.23` 是**单侧**值却叫「符号检验」——
方向没有事先指定，双侧才对，真值 0.453。用单侧让 p 看起来小了一半。）

而且第一版还写了「**没有位置偏好**」——那是**接受零假设**。n=7 根本没有功效
把「系统效应」和「位置效应」分开：sys-A 的优势（5:2）和直答的优势（5:2）大小完全相同。
诚实的说法是**这份数据分不开这两种解释**，所以才需要换一份 packet 重判。

### confidence 指纹（属实，已修）

第一版 packet 把 `概念(置信度)` 原样印了进去。这是一个 100% 准确的身份指纹：

```
14B  首概念 confidence 只用   {0.9: 22, 0.95: 5}
直答 还会出                  {0.85: 8, 0.8: 4, 0.75: 1}
⇒ 规则「首置信度 ∉ {0.9, 0.95} ⇒ 直答」在 13/29 条上适用且全对
  其中 5 条（as-05/09/22/25/29）落在决定分差的那 7 条里
```

RUBRIC 的主分本来不需要 confidence，所以重出了一份不印 confidence 的 packet
（`judge-packet-r8b.md`，换种子重新指派）并重判。

**结果：指纹不是在给直答加分。** 去掉它之后直答的优势反而从 +0.103 扩大到 +0.172。
但这不改变上面的结论——仪器噪声比效应大，两轮都测不出显著差别。

判官逐条的**定性**观察在两轮里高度一致，而且可核对：
三条「看到关键词就跳到邻近领域」的误标（`as-07` 把用大模型写代码标成 `算法推荐`、
`as-09` 把自动化抄发票标成 `工作替代`、`as-22` 把职场生育追问标成 `亲密关系`）
**两轮都出现、两轮都属于 14B**。反过来 14B 赢的两条（`as-05` 漏掉 `原生家庭`、`as-25`）
两轮也都是直答只给一个词、漏掉可辨识的那一半。

**两边各有一种系统性的失分方式。定性结论稳，定量的 0.1 不稳。**

### 这个比较哪里**不**对称（先自己说，别等人来挑）

| 变量 | 14B | 直答 | 实际影响 |
|---|---|---|---|
| prompt / 输入 / 校验 / 判分 | 完全相同 | 完全相同 | 无 |
| JSON mode | ✅ `format:'json'` 由推理引擎保证 | ❌ **没有** | 对直答不利 |
| `temperature` | 0.2（生效） | 0.2（实测被忽略） | 对直答不利 |
| `maxAttempts` | 2 | 4 | **对直答有利**：它的 29/29 靠了 1 次重试，单次 28/29 |
| 超时 | 120s | 60s | 都没触发 |
| 请求间隔 | 无 | 5s | 只影响限速，不影响质量 |

`maxAttempts` 这条不是可忽略的小事：它正是让「28/29」变成「29/29」的原因。

### 并列裁决规则的适用性

`RUBRIC.md` 第五节原文是：「若**较小模型**已过全部 Gate，则**较大模型**必须
高出 ≥0.25 才允许被选中；否则选**满足需求的最小模型**」——它是为**模型大小**
写的反偏置规则。本地 14B vs 云端直答之间**没有「较小/较大」的序**，
把 0.25 当成一般显著性阈值是**规则挪用**，所以不再引用它。

判定「测不出差别」靠的是上面那张判官漂移表 —— 本轮实测的，不是借来的。

（另：`make-packet-r8.ts` 曾写「rubric 一个字没改」。实际第五节逐字未改，
但全文哈希与 `FROZEN.md` 记录不一致，那是 `970cc0c` 澄清 `padding fail` 分母
22→23 造成的，与本轮无关。措辞已改准。）

## 六、Production Provider 决定：PROFILE A · 直答

质量测不出差别，所以选型**不是**靠质量决定的。

### 先说清一件容易被讲成"今天的发现"的事

「14B 没过 p50 ≤ 8s 这条 Gate」**不是本轮发现的**。
`bench/model-select/score-report.json` 从 R5 起就写着：

```json
"chosen": "qwen2.5:14b",
"decision": "没有模型通过全部 Gate。按主分最高选 qwen2.5:14b，并把未过的 Gate 明确写进报告——不改 Gate。"
qwen2.5:14b  gate {schema:true, zeroRate:true, p50:false, p90:true}  gatePass false
```

也就是说：**九天前就知道 14B 违反了自己冻结的 Gate，而且照样把它作为生产默认发了出去**——
当时把这件事如实写进了报告、没有去改 Gate，这一点是对的。

今天变的不是「14B 过不过 Gate」，而是**第一次出现了一个过 Gate 的候选**。
诚实的说法是这个，不是"我们今天发现 14B 不达标所以换掉它"。

Gate 对账：

| Gate（跑之前冻结） | 14B | 直答 |
|---|---|---|
| schema 成功 ≥ 98% | ✅ 100%（单次） | ⚠️ 单次 **96.6%** 未过；重试后 100% |
| 主分 0 占比 ≤ 10% | ✅ 3.4% | ✅ 3.4% |
| **p50 ≤ 8s** | ❌ **9.354s** | ✅ 2.218s |
| p90 ≤ 15s | ✅ 11.278s | ✅ 2.984s |

**14B 没过 Gate 3（p50）。直答没过 Gate 1 的单次口径（96.6% < 98%），重试后过。**

两个都不是干干净净四条全过。差别在于：直答差的那条靠一次重试就补上了（成本 1 次配额、
额外几百毫秒）；14B 差的那条是**架构性的**——p50 9.4 秒是本地 14B 在这台机器上的物理下限，
没有任何重试能把它变成 8 秒以内。

再加上一条和模型质量无关、但会当场毁掉演示的事实：14B 要在 16GB 的演示机上常驻 9.5GB。
上一轮实测，开着几个 Electron 应用时 ollama 每次请求后就把模型驱逐掉，
预热从 34 秒涨到 124 秒，一个 5 token 的请求要 280 秒。

所以：

```
PROFILE A · ZHIDA_LIVE   知乎官方直答      ← 默认，比赛用这个
PROFILE B · LOCAL_LIVE   本地 qwen2.5:14b  ← 降级：断网 / 额度耗尽 / 官方故障
PROFILE C · DEMO         确定性演示数据     ← 只在扩展侧，面板必须打「演」标记
```

**绝不静默降级**：`ZHILIU_PROVIDER=zhida` 但没有 Access Secret → 服务**拒绝启动**并
打印三个明确选项，不会偷偷换成 ollama。`/health` 如实上报当前 provider 与 model，
每条结果的 `provenance.provider` 也如实写 `zhida`。

### 额度耗尽路径**没有测**（诚实补充）

第四节那句「HTTP 200 是不是假成功？**不是。**」的依据是实测过 401 / 400 / 429 三种。
**额度耗尽不在其中**，而它恰好是唯一真正会在赛中发生的失败模式。

官方 `http-api.md` 对 `Code/Message` 信封的接口写明「频率、并发限制和日额度耗尽
均返回 30001，遇到限制时**避免持续重试**」；但直答走的是 OpenAI 形状而不是那个信封，
所以**耗尽到底返回什么，没人知道**。推测是 429，但没测，也不打算为了测它去烧掉 5000 次额度。

代码上现在的行为：若耗尽表现为 429，`ZhidaExtractor` 会**每一篇**都打 2 次、睡 2 秒，
然后报 `provider_http_429_rate_limit_exceeded`。**没有熔断**，没有把
「限速（等一下就好）」和「今天没了（别再试）」区分开——这与官方的「避免持续重试」相反。
见 `CLAIM_EVIDENCE.md` 的 U-11。

### 新的风险：从「内存」换成了「网络 + 限速」

选直答消掉了 9.5GB 内存和 40–120 秒冷加载，但换来了三个新的失败面：
**评审侧网络**、**限速**、**官方服务可用性**。三个都不在我们手里。
（本项目线上提交 + 远程评审，评委不接触作者本机，所以这里的网络指的是
公网 backend 到 developer.zhihu.com 这一段，不是任何线下场地的接入。）
所以 PROFILE B 必须保持能一条命令切回去，runbook 里也写死了这一步。

## 七、这次**没有**做的事（以及为什么）

| 能力 | 状态 | 理由 |
|---|---|---|
| OAuth / 知乎登录 | **没做** | 官方文档说可独立接入。人气奖看登录用户数，所以它是 P1；在核心链路稳定之前动它，是拿最后 48 小时赌一个加分项 |
| `hot`（热榜） | 没接 | 知流是「让你自己的信息流可见」，不是再推一个热点榜 |
| `knowledge`（知识库） | 没接 | 和产品主张无关 |
| `question recommend` | 没接 | 那是帮你**写**回答，知流管的是你**读**了什么 |
| `global_search` | 没接 | 概念溯源要的是知乎语境，不是全网 |
| 把 Search 塞进主链路 | **刻意不做** | 见第三节：它不提高准确率，塞进去只会让每篇分析多一次网络往返和一次配额 |

接了几个官方 API 不是评分项。**不可替代的价值**才是。
直答是不可替代的（它替掉了整个本地模型）；搜索是有条件可用的；其余对这个产品没有价值。
