# 判别机制：为什么知乎官方 API 是承重结构，而不是装饰

> 本文回答评委最可能追问的两个问题：
> **「为什么普通关键词统计不够？」** 和 **「为什么非得是知乎的 API？」**

## 1. 失败模式

一篇讲相亲经历的知乎回答，可能反复出现：

```
女性 · 男性 · 约会 · 外貌 · 异性
```

朴素系统会归到「性别议题」。但作者真正在讲的是：

```
紧张 · 回避 · 别人怎么看我 · 事后反复回放
```

也就是**社交焦虑 / 负面评价恐惧**。

这个错误不会停在一篇文章。它会沿着链路放大：

```
概念判错 → 占比错 → 趋势错 → 信息集中度错 → 整个面板不可信
```

所以本项目的技术核心不是画图，是**判对中心思想**。

## 2. 为什么"再问一次大模型"不够

直觉方案是让 LLM 直接分类。问题在于：LLM 用的是**它自己的先验**。
当表层词与真实主旨冲突时，先验很容易被高频词牵着走——而且它的错误是
**不可解释、不可复现、不可调试**的：你没法回答"它为什么这么判"。

我们需要的是一个**外部的、可检查的语义参照系**。

## 3. 机制：跨邻域 IDF 判别

### 3.1 建立语义邻域

对每个候选概念 `c`，用官方 `zhihu_search` 取回它在知乎社区里的 Top-N 内容：

```
N(c) = zhihu_search(Query=c, Count=8).Data.Items
```

把 `Title`（×3 权重）+ `ContentText` + 精选评论压成一个加权词频画像，
权重按官方给的 `RankingScore` 缩放：

```
profile(c)[t] = Σ_{item ∈ N(c)} (1 + RankingScore_item) × tf(t, item)
```

这就是「概念 c 在知乎上实际是怎么被谈论的」。

### 3.2 关键一步：用什么词来判断

**不是**比较原文和哪个邻域更像——那样共享的表层词会主导结果。
而是先问：**哪些词具有区分力？**

对候选集合中的每个词 `t`：

```
df(t) = 含有 t 的候选邻域数量
w(t)  = ln(1 + m / df(t))          m = 候选数
```

于是：

| 词 | 出现在 | df | 权重 | 结果 |
| :- | :- | :- | :- | :- |
| 女性 / 约会 / 外貌 | 性别议题邻域 **和** 社交焦虑邻域 | 高 | ≈ 0 | **失去话语权** |
| 结构 / 权利 / 彩礼 / 歧视 | 只在性别议题邻域 | 低 | 高 | 成为性别议题的证据 |
| 紧张 / 回避 / 心跳 / 事后回放 | 只在社交焦虑邻域 | 低 | 高 | 成为社交焦虑的证据 |

最终得分：

```
score(c) = Σ_t  w(t) · tf_article(t) · profile(c)[t]
```

原文里那些"两个邻域都有"的词被自动中和掉，剩下的独特词决定归属。

### 3.3 为什么这解决了问题

因为**判别用的词表不是我们写死的，也不是模型的先验，而是查询时从知乎语料现算出来的**。

我们从未在任何地方写过"女性这个词不能用来判断性别议题"。
是知乎语料自己告诉我们：这个词在两类讨论里都同样常见，所以它没有区分力。

## 4. 为什么必须是知乎的语料

三个具体理由，都可以当场演示：

1. **重叠结构是语料特有的。** 「女性/约会/外貌」在知乎的社恐讨论里高频，是因为
   知乎上大量社交焦虑话题就发生在相亲、饭局、职场社交场景。换一个语料库
   （比如学术语料或新闻语料），这两个概念的邻域几乎不重叠，IDF 就压不到该压的词，
   机制会退化。

2. **词汇是社区方言。** 「社恐」「上岸」「内耗」「emo」这些词，只有在知乎自己的
   语料里才会与对应概念高频共现。通用词典和预训练先验都拿不到这种时效性表达。

3. **`RankingScore` 是官方信号。** 邻域加权用的是知乎自己的相关性排序分，
   而不是我们编的启发式。这一点无法从站外复现。

> 一句话：**我们不是"调用了知乎 API"，而是"把知乎语料当成判别器的一部分"。
> 把 API 拿掉，`df(t)` 无从计算，判别函数本身就不存在了。**

## 5. 不使用哪些字段，以及为什么

官方 `zhihu_search` 还返回 `AuthorityLevel`、`VoteUpCount`、`CommentCount`。
本项目**刻意不用**它们：

它们衡量的是**内容质量与热度**，而本项目判断的是**语义归属**。
用点赞数加权会让判别偏向热门话题——一篇冷门但精准的社交焦虑讨论，
不应该比一篇高赞的泛泛而谈更没有代表性。

这条边界同时也是产品边界：知流不评价内容好坏，只描述你接触了什么。

## 6. 成本：为什么这套设计跑得起

官方限额：知乎搜索 **5,000 次 / 日**（`zhihu-cli quota` 2026-09-13 实测；
此处原写的 1,000 是按"保守取值"猜的，已作废）。日额度其实很宽，真正的约束是瞬时限速。

朴素实现每篇文章要 3–5 次搜索，看起来 200–330 篇就打满了。但是：

**搜索 query 的取值空间是有界的。** 候选概念只能来自固定的 31 个 canonical 注册表，
所以 query 只有 31 种可能。配合 24h 缓存，稳态下每天的上游调用量上限是

```
≈ 概念数（31） 而不是 文章数
```

这是"用固定概念表做召回"这个设计的第二个好处——第一个是面板不碎裂。

## 7. 诚实的边界

- **判别质量依赖候选召回。** 如果 gold 概念根本没被召回进候选，Grounding 也救不回来。
  benchmark 中单独统计了这类 `over_abstain` / `missed_gold`。
- **字符 bigram 不是语义理解。** 它捕捉的是用词分布相似性。对反讽、隐喻、
  极短文本无效——这正是系统必须允许输出 `unknown` 的原因。
- **本仓库当前的评测跑在离线语料上。** 见 README「当前状态」一节。

## 附：知乎 DOM 解析的未验证点

**本仓库的 selector 尚未在真实知乎页面上验证过。**

尝试用自动化浏览器打开 `https://www.zhihu.com/question/...` 时，
知乎会重定向到 `安全验证 - 知乎`（`/account/unhuman?...&need_login=true`）——
自动化访问拿不到真实 DOM。我们**没有**绕过该验证，这既是规则要求，
也是官方 API 使用规范里明确禁止的行为。

因此以下几点必须由人在自己已登录的 Chrome 里实测确认：

| 待验证 | 当前假设 |
| :- | :- |
| 回答独立页正文容器 | `.QuestionAnswer-content .RichText` |
| 专栏文章正文容器 | `.Post-RichTextContainer .RichText` |
| 问题页多回答场景 | 目前取第一个匹配，**可能取错**当前视口内的那条回答 |
| 标题 | `h1.QuestionHeader-title` / `h1.Post-Title` |
| SPA 路由切换 | 每 1.5 秒轮询 URL 变化后重开会话 |

缓解措施：`extract-content.ts` 增加了 `largestTextBlock()` 兜底——
所有 selector 落空时，按"文本量最大且文本密度足够高"的启发式抽取正文，
并靠 `MIN_TEXT_CHARS` 阈值挡掉抽取失败的页面（不计入有效阅读，不污染统计）。

**已知最大的未解决问题是「问题页多回答」**：用户在一个问题页往下滚，
会连续经过多条回答，当前实现只会认第一条。V0.1 的取舍是先只在回答独立页
和专栏文章页保证正确；问题页的分回答归属留到 P1。
